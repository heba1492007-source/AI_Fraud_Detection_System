## Goal

Financial services companies process thousands of transactions per day and need an intelligent system that can automatically flag suspicious transactions for further investigation, reducing financial losses caused by fraud.

This project builds such a system end-to-end: data exploration → cleaning → feature preparation → model training/evaluation → an interactive app to test new transactions.

## Dataset

- **Name:** Credit Card Fraud Detection
- **Source:** [Kaggle — mlg-ulb/creditcardfraud](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud)
- **Size:** 284,807 transactions, 492 labeled as fraud (~0.17%) — highly imbalanced
- **Features:** `Time`, `V1`–`V28` (anonymized, PCA-transformed), `Amount`
- **Target:** `Class` (`0` = Normal, `1` = Fraud)

The dataset file (`creditcard.csv`) is **not included** in this repository due to its size. See [`data/README.md`](data/README.md) for download instructions.

## Methodology

1. **Exploratory Data Analysis** — inspect the data, check missing values, check duplicates, and visualize the (highly imbalanced) class distribution.
2. **Data Cleaning** — remove duplicated rows.
3. **Preprocessing** — split features (`X`) and target (`y`), then apply `StandardScaler` to normalize numerical features.
4. **Train/Test Split** — 80/20 split, stratified on the target so both sets keep the same fraud ratio.
5. **Handling Class Imbalance** — with only ~0.17% of transactions labeled fraud, a model trained directly on the raw data (even with `class_weight="balanced"`) tends to over-correct: it flags almost everything as fraud, so Recall looks great but Precision collapses (this is exactly what happened with the first version of Logistic Regression — see [Why SMOTE instead of just `class_weight`](#why-smote-instead-of-just-class_weight) below). To fix this properly, **SMOTE** (Synthetic Minority Over-sampling Technique) is applied to generate synthetic "Fraud" samples so the model sees a balanced training set.
   - SMOTE is fit **only on the training set**, *after* the train/test split. The test set is left at its real, imbalanced distribution — this avoids leaking synthetic information into evaluation and keeps the reported metrics honest about real-world performance.
6. **Model Training** — four classifiers are trained on the SMOTE-balanced training set:
   - Logistic Regression
   - Decision Tree
   - Random Forest
   - **XGBoost** (gradient boosting — usually the strongest performer on tabular fraud data)
7. **Model Evaluation** — each model is scored on **Precision**, **Recall**, **F1 Score**, and a **Confusion Matrix**, since plain **Accuracy is misleading** on an imbalanced dataset like this one (a model that predicts "Normal" for everything would still score >99% accuracy while catching zero fraud).
8. **Model Selection** — `train_model.py` automatically picks the model with the **highest F1 Score** (the best balance between Precision and Recall) across all four models and saves it as `models/best_model.pkl`, instead of assuming any single algorithm in advance.

## Model Evaluation & Selection

| Metric | What it tells us |
|---|---|
| **Precision** | Of all transactions flagged as fraud, how many actually were fraud? |
| **Recall** | Of all actual fraud transactions, how many did the model catch? |
| **F1 Score** | Harmonic mean of Precision and Recall — the metric used to pick the best model |
| **Confusion Matrix** | Full breakdown of True/False Positives and Negatives |

### Why SMOTE instead of just `class_weight`?

An earlier version of this project trained on the raw imbalanced data using only `class_weight="balanced"`. The result was a warning sign, not a win:

| Model | Precision | Recall | F1 Score |
|---|---|---|---|
| Logistic Regression | ~0.05 | ~0.87 | ~0.10 |
| Decision Tree | ~0.73 | ~0.63 | ~0.67 |
| Random Forest | ~0.96 | ~0.70 | ~0.81 |

Logistic Regression's Recall looks strong, but its Precision is almost 0 — it was flagging huge numbers of normal transactions as fraud, which is unusable in production (way too many false alarms for a fraud team to review). Random Forest's `class_weight` handled it better because trees can naturally isolate the minority class, but it was still leaving Recall (fraud caught) on the table.

Adding **SMOTE** on top of a proper train/test split (train set balanced, test set left untouched) is a more direct fix: instead of just re-weighting the loss function, it gives every model — including **XGBoost** — actual balanced examples to learn from. This is what makes it possible for XGBoost to reach a **high Precision *and* high Recall at the same time**, rather than trading one off against the other.

## Results

These are the actual results from running `python src/train_model.py` on the full dataset (284,807 transactions, 492 fraud). Metrics are computed on the held-out **test set only** (20%, left at the real-world imbalance — SMOTE was never applied to it), so they reflect realistic production performance, not inflated numbers from a balanced test set.

| Model | Precision | Recall | F1 Score |
|---|---|---|---|
| Logistic Regression | 0.0530 | 0.8737 | 0.1000 |
| Decision Tree | 0.3526 | 0.6421 | 0.4552 |
| **Random Forest** | **0.9125** | **0.7684** | **0.8343** |
| XGBoost | 0.7238 | 0.8000 | 0.7600 |

**Best model: Random Forest** (highest F1 Score), selected automatically by `train_model.py` — not hardcoded.

**Random Forest confusion matrix** (test set, 56,746 transactions):

| | Predicted Normal | Predicted Fraud |
|---|---|---|
| **Actual Normal** | 56,644 | 7 |
| **Actual Fraud** | 22 | 73 |

Reading it: out of 95 real fraud transactions in the test set, Random Forest caught 73 of them (77% Recall) while only misflagging 7 normal transactions as fraud out of 56,651 (91% Precision) — a strong balance for a fraud-review workflow, where both missed fraud and false alarms are costly.

Logistic Regression illustrates exactly the [SMOTE vs `class_weight`](#why-smote-instead-of-just-class_weight) problem in practice: 87% Recall looks great on paper, but its Precision of 5% means it flagged **1,482 normal transactions** as fraud just to catch 83 real ones — unusable for an actual fraud team.

All four `confusion_matrix_*.png` images and the full `evaluation_results.json` are in `results/`.

## Installation & Setup

```bash
# 1. Clone the repository
git clone <your-repo-url>
cd AI_Fraud_Detection_System

# 2. Create a virtual environment (recommended)
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Download the dataset (see data/README.md) and place it at:
```

## How to Run

**1. Train the models** (also saves the best model + evaluation results):

```bash
python src/train_model.py
```

**2. Run a quick CLI prediction demo:**

```bash
python src/predict.py
```

**3. Launch the Streamlit app:**

```bash
streamlit run app.py
```

Then open the URL shown in the terminal (usually `http://localhost:8501`). You can click **Load Fraud Example** to auto-fill a known fraud transaction, or enter your own values, then click **Predict Transaction**.

## Possible Improvements

- Add hyperparameter tuning (`GridSearchCV` / `RandomizedSearchCV`, or `Optuna` for XGBoost specifically) instead of default parameters.
- Add cross-validation (e.g. `StratifiedKFold`) instead of a single train/test split for more robust metrics.
- Add a `ROC-AUC` / `Precision-Recall AUC` curve and plot it — more informative than a single threshold's Precision/Recall on imbalanced data, and useful for picking a custom decision threshold (e.g. optimizing Recall since missed fraud is usually costlier than a false alarm).
- Try `LightGBM` / `CatBoost` alongside XGBoost, and try alternative imbalance techniques (`SMOTETomek`, `ADASYN`, or plain undersampling) to compare against SMOTE.
- Containerize the app with Docker for easier deployment.
- Add automated tests for `predict_transaction()` and for the SMOTE/training pipeline.
- Add feature importance / SHAP plots for the best model, to explain *why* a transaction was flagged (useful for a fraud analyst reviewing the app's output).
